# 0003: User and Workspace Authentication (Session Cookies vs JWT)

## Status

Accepted - 2026-11-14

## Context

FormFlow is an interactive web application where users sign up, create organizations/workspaces, invite collaborators with role-based permissions (owner, admin, member), build forms, and view sensitive submission responses. We must decide on the authentication and session management mechanism for user logins.

## Decision

We choose **server-side session cookies** (`HttpOnly`, `Secure`, `SameSite=Lax`) backed by Redis/PostgreSQL.

## Alternatives Considered

- **Stateless JSON Web Tokens (JWT) in Browser Storage (localStorage / sessionStorage)**:
  - _Pros_: Completely stateless; no session lookup required per request.
  - _Cons_: Highly vulnerable to Cross-Site Scripting (XSS) token exfiltration. Crucially, stateless tokens cannot be immediately revoked when a user changes their password, is removed from a workspace, or when a session is terminated by an administrator, unless a server-side denylist is introduced (which negates the stateless benefit).
- **JWT in HttpOnly Cookie**:
  - _Pros_: Immune to XSS token theft.
  - _Cons_: Still suffers from the instant revocation problem without maintaining state on the server.

## Consequences

### Positive

- Instant session revocation capability (e.g., "log out of all devices", role downgrade, or immediate account suspension).
- Complete mitigation of JavaScript-based credential theft via `HttpOnly` cookie flags.
- Simplified frontend code: browsers automatically send cookies on same-origin requests without requiring custom token interceptors or refresh token rotation logic in JavaScript.
- Ultra-fast session verification via in-memory Redis session caching.

### Negative

- Requires server-side storage overhead for active sessions (managed via Redis TTL).
- State-changing endpoints require CSRF protection measures (handled via SameSite cookies and standard anti-CSRF tokens).
